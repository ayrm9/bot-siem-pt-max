# MPSIEM-MAX-notification

Отправка инцидентов из MaxPatrol SIEM 10 в бот мессенджера **MAX**.

Порт проекта [SanyaClaus/MPSIEM-Telegram-notification](https://github.com/SanyaClaus/MPSIEM-Telegram-notification)
с Telegram Bot API на [Bot API мессенджера MAX](https://dev.max.ru/docs-api).
Логика работы с SIEM не менялась: написано для версии 26.0.4827, проверялось на 26.1.7351.

## Настройки

В файле `settings.py` находятся настройки бота.

Параметры SIEM:

- `dbFileName` - путь к файлу, в котором будут сохраняться данные бота (временные метки последних инцидентов, marker событий MAX, разрешенные чаты)
- `pause_time` - время в секундах между проверками инцидентов
- `time_zone` - часовой пояс (в SIEM события хранятся с временем по GMT+0, соответственно для отображения времени по Москве нужно задать +3 часа)
- `username` - имя пользователя в SIEM
- `password` - пароль пользователя в SIEM
- `client_id` - идентификатор приложения (mpx, ptkb)
- `client_secret` - ключ доступа к приложению в SIEM
- `base_url` - url для входа в SIEM (строго без символа `/` в конце строки)
- `default_header` - заголовок запросов, с которыми будет обращаться бот к SIEM
- `max_events_count` - максимальное число событий инцидента в сообщении

Параметры MAX:

- `max_api_url` - адрес Bot API MAX (по умолчанию `https://platform-api2.max.ru`)
- `max_bot_token` - токен бота MAX
- `max_updates_timeout` - время ожидания новых событий в MAX (long polling, максимум 90 секунд)
- `max_updates_limit` - сколько событий забирать из MAX за один запрос
- `max_admin_chat_id` - id чата с администратором в MAX
- `max_proxys` - словарь прокси для связи с MAX, пустой `{}` - без прокси
- `max_verify_ssl` - проверять ли сертификат сервера MAX
- `max_message_length` - максимальная длина текста сообщения (MAX обрезает длинные сообщения)
- `ping_sticker_code` - код стикера для ответа на `/ping`; если пусто, бот отвечает текстом

`client_secret` для авторизации скрипта в SIEM можно взять в конфигурации Core
(*/var/lib/deployed-roles/mp10-application/core-##########/install.sh*).

`max_bot_token` берется в личном кабинете [business.max.ru](https://business.max.ru/) в настройках чат-бота
(поле «Токен доступа», рядом есть кнопка копирования и кнопка перевыпуска). Второй способ - создать бота
у [@masterbot](https://max.ru/masterbot) прямо в мессенджере: команда `/newbot`, затем `/mybots` для просмотра
токена.

Чтобы узнать `max_admin_chat_id`, напишите своему боту любое сообщение и запустите `check_settings.py` -
он покажет chat_id всех, кто писал боту. Вручную то же самое:

```
curl -H "Authorization: ВАШ_ТОКЕН" "https://platform-api2.max.ru/updates?limit=100&timeout=3"
```

В событии `message_created` нужное значение лежит в `message.recipient.chat_id`. Тот же id бот выведет
в лог при получении сообщения.

### Авторизация в Bot API MAX

Две особенности, на которых легко споткнуться:

- токен передается в заголовке `Authorization` **без префикса `Bearer`**. С префиксом MAX считает токеном
  всю строку целиком и отвечает `401 {"code":"verify.token","message":"Malformed access token"}`;
- параметр `access_token` в query больше не поддерживается, ответ на него -
  `401 {"message":"Query parameter access_token is deprecated, use Authorization header"}`.

Домен API тоже переехал: `botapi.max.ru` -> `platform-api.max.ru` -> актуальный `platform-api2.max.ru`.

## Установка и запуск

```
pip install -r requirements.txt
python3 check_settings.py                      # проверка настроек и связи
python3 mp-siem-max-bot-notification.py        # запуск
```

`check_settings.py` по очереди проверяет заполненность `settings.py`, токен MAX, авторизацию в SIEM и
чтение инцидентов, а также показывает `chat_id` тех, кто уже писал боту - оттуда берется
`max_admin_chat_id`. При каждой проблеме печатается подсказка, что именно поправить. Бота на время
проверки лучше остановить.

Скрипт одинаково работает как на Windows, так и на Unix-подобной системе. Нужен Python 3.7 и новее,
из внешних зависимостей только `requests`.

При первом запуске файл БД будет создан автоматически по пути, указанному в параметре `dbFileName`.

Для работы под Linux рекомендуется запуск бота в качестве сервиса. Скопируйте `mp-siem-max.service`
в `/etc/systemd/system/`, укажите в нем путь к каталогу со скриптом и к интерпретатору, затем:

```
systemctl daemon-reload
systemctl enable mp-siem-max.service # включить автостарт
systemctl start mp-siem-max.service  # запуск сервиса
systemctl status mp-siem-max.service # статус сервиса
systemctl stop mp-siem-max.service   # остановка сервиса
```

## Выдача доступа к оповещениям

После создания файла БД таблица `max_chats_allowed` не содержит записей, то есть оповещения об инцидентах
не будут отправляться никому.

Когда пользователь нажимает в боте кнопку «Начать» (событие `bot_started`) или отправляет команду `/start`,
администратор получает сообщение с кнопками:

- ✅ **Разрешить** - отправлять оповещения об инцидентах в этот чат;
- ⏹ **Проигнорировать** - не отправлять оповещения в этот чат;
- ⛔️ **Заблокировать** - больше не получать запросы на доступ от этого чата.

То же сообщение приходит администратору при добавлении бота в групповой чат (событие `bot_added`).

Если администратор не нажал ни одну из кнопок, чат в список рассылки не попадает.

Вместо кнопок можно использовать команды, они же нужны для добавления администратором самого себя:

- `/accept 123456789` - разрешить отправку оповещений в чат по id
- `/accepted` - список чатов, куда отправляются оповещения
- `/deny 123456789` - перестать отправлять оповещения в чат по id
- `/ban 123456789` - заблокировать чат: не обрабатывать его события и не оповещать о нем администратора
- `/unban 123456789` - убрать чат из списка заблокированных
- `/banned` - список заблокированных чатов
- `/ping` - проверка работоспособности бота (доступна разрешенным чатам)
- `/debug` - текущие переменные и последние логи
- `/help` - список команд

Команды принимаются и в слитном виде, как в Telegram-версии: `/accept123456789`, `/deny-123456789`.

## Работа бота

Бот авторизуется в SIEM и получает токен, с которым осуществляет все дальнейшие обращения к SIEM по API.

Если токен закончится (обычно через 24 часа) и будет получена ошибка 401 (Unauthorised), будет выполнен
новый запрос на получение токена.

Если в SIEM появляются новые инциденты, информация о них отправляется в разрешенные администратором чаты.
Под сообщением об инциденте бот рисует inline-клавиатуру:

- 🔄 **Обновить** - перечитать инцидент из SIEM и обновить сообщение;
- ▶️ **Подтвердить** - перевести инцидент в статус `Approved` (только для новых инцидентов);
- ⏹ **Закрыть** - перевести инцидент в статус `Closed` (только для новых инцидентов).

В комментарий к смене статуса в SIEM попадает имя пользователя MAX, нажавшего кнопку.

Администратором является пользователь, указанный в параметре `max_admin_chat_id`.

## Тестирование

В каталоге `tests/` лежат эмуляторы обоих API и сквозной тест. Ни MAX, ни SIEM для прогона не нужны -
бот запускается без изменений, но смотрит на localhost.

```
python3 tests/run_e2e.py
```

Тест поднимает эмуляторы, копирует скрипты бота во временный каталог с подменённым `settings.py`,
запускает бота и проверяет полный цикл: авторизацию в SIEM по 401, long polling с `marker`, выдачу
доступа новому чату через кнопки, доставку инцидента с клавиатурой, смену статуса в SIEM по нажатию
кнопки с правкой уже отправленного сообщения, команды, чёрный список и сохранение состояния при
перезапуске. В конце печатается отчёт и путь к логам.

Нужны свободные порты 80 и 3334 (эмулятор SIEM подставляется вместо `base_url`, бот сам добавляет
`:3334` для получения токена) и 8765 (эмулятор MAX). Порт 80 требует прав root.

Эмуляторы можно запускать и по отдельности, чтобы поиграть с ботом руками:

```
python3 tests/fake_siem.py &
python3 tests/fake_max.py 8765 &
```

У них есть служебные ручки, которых нет в настоящих API:

| Ручка | Назначение |
| --- | --- |
| `POST http://127.0.0.1:8765/_inject` | положить событие в очередь `/updates` |
| `GET http://127.0.0.1:8765/_state` | отправленные сообщения, правки, ответы на кнопки |
| `POST http://127.0.0.1/_add_incident` | создать инцидент в SIEM |
| `GET http://127.0.0.1/_state` | инциденты и история смен статуса |
| `POST .../_reset` | очистить состояние |

## Чем отличается от Telegram-версии

Порт затрагивает только транспорт: запросы к SIEM, формат сообщений об инцидентах и логика выдачи доступа
сохранены. Существенные различия Bot API MAX и Telegram Bot API, которые пришлось учесть:

| | Telegram | MAX |
| --- | --- | --- |
| Адрес API | `https://api.telegram.org/bot<token>/<method>` | `https://platform-api2.max.ru/<method>` |
| Авторизация | токен в пути URL | заголовок `Authorization: <токен>`, без `Bearer` |
| Курсор событий | `offset` = `update_id` + 1 | `marker` из ответа `/updates` передается как есть |
| Отправка | `sendMessage`, `chat_id` в теле | `POST /messages`, `chat_id` в query, разметка в поле `format` |
| Клавиатура | отдельное поле `reply_markup` | вложение `attachments` с типом `inline_keyboard` |
| Редактирование | `editMessageText` по `chat_id` + `message_id` | `PUT /messages?message_id=<mid>`, вложения нужно передать заново |
| Ответ на кнопку | `answerCallbackQuery` | `POST /answers?callback_id=<id>` |
| Команды | приходят с `entities` типа `bot_command` | `entities` нет, команда определяется по тексту |
| Нажатие «Начать» | `/start` как обычное сообщение | отдельное событие `bot_started` |
| Добавление в чат | `my_chat_member` со статусом `member` | события `bot_added` и `bot_removed` |
| Тип чата | групповые чаты имеют отрицательный id | id всегда положительный, тип берется из `chat_type` |
| Стикеры | можно отправить ссылку на GIF или `file_id` | отправляется вложение `sticker` по коду стикера |
| Кнопки | только текст | у кнопки есть `intent`: `default` / `positive` / `negative` |

Изменились имена таблиц в БД бота (`max_chats_allowed`, `max_chats_denied`) и переменная курсора событий
(`last_marker` вместо `last_update`), поэтому база от Telegram-версии не подходит - при первом запуске
создается новая.

Заодно исправлены расхождения имен настроек из Telegram-версии (`settings.proxys` против `tg_proxys`,
`settings.admin_chat_id` против `tg_admin_chat_id`), а запросы к SQLite переведены на подстановку параметров.
